# Execution & Hosting Improvement Plan (2026-11-14)

## Review update (2026-11-15)

Only this dated plan is active. Source inspection found three stale premises in
the original roadmap:

1. `ExecutionWorker.Process` already creates its session before completing
   startup. Pool startup is already parallel. **EX-02 is a regression gate**:
   preserve eager startup, failure cleanup and readiness semantics. Do not add a
   default-false warm-up option that makes existing startup lazy.
2. `ExecutionWorkerSnapshot`, `ExecutionWorkerPoolSnapshot` and `GetSnapshot`
   already exist. **EX-04 extends those types only as needed for hosting health
   checks**; do not introduce a competing snapshot model. A per-worker array is
   allocated today, so do not claim zero-allocation snapshots without measuring
   and implementing a different storage contract.
3. `QueueCapacity` and atomic admission already exist, including requests
   admitted during startup. **EX-05 preserves that option and its established
   `InvalidOperationException` behavior**. Test/measure it instead of adding
   incompatible `MaxQueueDepth` options or a new mandatory exception contract.

Remaining implementation requirements:

- **EX-01:** contextual creation/disposal receives a stable worker slot/count
  and the same generation for both ends of a session lifetime. Increment only
  for a successfully created replacement. Cover count-based and fault-based
  recycles, creation/disposal failures, two pools and at least 50 recycles per
  slot. Add indexed DI/Hosting overloads without changing existing factories.
- **EX-03:** add dispatcher extension overloads instead of abstract members on
  existing interfaces (legacy TFM implementers remain binary compatible).
  A deadline bounds the entire caller wait, including startup and queueing.
  Return promptly even while synchronous native work continues; keep the
  worker/session occupied until it really finishes. A queued expired item never
  runs. Preserve the caller's exact cancellation token and define races with
  already-completed work. Keep timer/linked-token resources alive until the
  underlying operation completes; never reset/reuse a CTS still observed by a
  running native delegate. Validate zero, infinite and timer-range boundaries.
- **EX-04:** health is not ready before eager startup completes; detect disposed
  pools, startup faults, partial worker loss and total worker loss. Configurable
  queue warnings use existing snapshot values. Keep health dependencies in the
  Hosting package and test the public DI/host entry points.
- **EX-06 (P0), startup ordering:** offer optional `BeforeThreadStart` wiring in
  worker/pool options, propagated through snapshots and DI. Run it on the caller
  before creating STA threads so COM/Nano preparation does not race across
  worker constructors. No hard dependency on COM or Threading is introduced.

Keep default native calls non-preemptive, shutdown ownership and telemetry
listener isolation unchanged. Source changes and validation must cover all
retained TFMs; no package publishing or consumer version upgrade is requested.

## Executive summary

`AdaskoTheBeAsT.Interop.Execution` `v2.2.0` (`ExecutionWorker<TSession>`, `ExecutionWorkerPool<TSession>`, `LeastQueuedWorkerScheduler<TSession>`, OpenTelemetry `Meter`/`ActivitySource`, and `ExecutionWorkerPoolHostedService<TSession>`) performed reliably across every service. At the same time, four pieces of boilerplate had to be copy-pasted across all 30+ host applications because the DI, factory, deadline, and health-check layers have small ergonomic gaps:

1. **Worker slot identity is lost in `AddExecutionWorkerPool<TSession>` and across session recycles:**
   - Core `ExecutionWorkerPool<TSession>` already has `Func<int, IExecutionSessionFactory<TSession>>` (`ExecutionWorkerPool.cs:95`), **but** `ExecutionWorkerServiceCollectionExtensions.AddExecutionWorkerPool<TSession>` (`ExecutionWorkerServiceCollectionExtensions.cs:96-100`) discards the worker index:
     ```csharp
     return new ExecutionWorkerPool<TSession>(
         _ => sp.GetRequiredService<IExecutionSessionFactory<TSession>>(),
         options,
         scheduler);
     ```
   - Consequently, `IExecutionSessionFactory<TSession>.CreateSession(CancellationToken)` (`IExecutionSessionFactory.cs:20`) has no knowledge of **which worker slot (`0..WorkerCount-1`)** or **which recycle generation (`0, 1, 2, ...`)** is creating the session! Session factories that prepare per-worker binary-patched native DLL copies (`engine_00.dll`, `engine_01.dll` — limited to 2-digit ASCII suffixes so PE string lengths stay invariant!) are forced to maintain manual `Interlocked.Increment` counters or `ConcurrentQueue<int>` slot pools, which drift above `WorkerCount` when `MaxOperationsPerSession` or `RecycleSessionOnFailure` recycles a session!
2. **Per-request execution deadline / pooled timeout token boilerplate:** Every service had to carry a custom `CalculationExecutionExtensions` helper with a `ObjectPool<CancellationTokenSource>` (`TryReset()`), linked caller + deadline token creation, and distinction between caller cancellation (`499` / `OperationCanceledException(callerToken)`) vs execution deadline expiry (`504` / `TimeoutException`).
3. **Readiness & health-check integration in `Execution.Hosting`:** Every ASP.NET Core service had to write custom `/readyz` and `/api/diagnostics` wiring over `IExecutionWorkerPool<TSession>` (`WorkerCount`, `QueueDepth`, `IsAnyFaulted`, `WorkerFaults`, and whether startup initialization has completed).
4. **Eager vs lazy session warm-up option on `ExecutionWorkerHostedService` / `ExecutionWorkerPoolHostedService`:** Currently `InitializeAsync` starts the dedicated OS `Thread`s, while `CreateSession` runs lazily on the first `ExecuteAsync` call (`IExecutionSessionFactory.cs:14-16`). For native/COM engines whose cold catalog/DLL initialization takes 150–800 ms (or whose binary/manifest validation should fail fast before `/readyz` turns green), hosts need an opt-in `WarmUpSessionsOnStart = true` setting.

## Detailed technical plan

### EX-01 (P0): Contextual session lifecycle (`SessionLifecycleContext`) & worker-indexed DI registration

#### Evidence
- `IExecutionSessionFactory<TSession>.CreateSession(CancellationToken)` (`src/AdaskoTheBeAsT.Interop.Execution/IExecutionSessionFactory.cs:20`) passes only `CancellationToken`.
- `ExecutionWorkerServiceCollectionExtensions.AddExecutionWorkerPool<TSession>` (`src/AdaskoTheBeAsT.Interop.Execution.DependencyInjection/ExecutionWorkerServiceCollectionExtensions.cs:97`) ignores the `int workerIndex` argument passed by `ExecutionWorkerPool<TSession>` (`_ => sp.GetRequiredService<IExecutionSessionFactory<TSession>>()`).
- Native isolation layers that patch fixed-length ASCII DLL names in PE import tables (`workerIndex` formatted as `00..99`) require a **stable bounded `WorkerIndex` (`0 <= WorkerIndex < WorkerCount`)** that stays identical when Worker `k` recycles its session after `MaxOperationsPerSession` or `RecycleSessionOnFailure`!

#### Design
1. Introduce an immutable `readonly struct SessionLifecycleContext` in `AdaskoTheBeAsT.Interop.Execution`:
   ```csharp
   public readonly struct SessionLifecycleContext
   {
       public int WorkerIndex { get; init; }
       public int WorkerCount { get; init; }
       public string WorkerName { get; init; }
       public long SessionGeneration { get; init; }
       public SessionRecycleReason? PreviousRecycleReason { get; init; }
       public int ManagedThreadId { get; init; }
   }

   public enum SessionRecycleReason
   {
       MaxOperationsReached = 0,
       OperationFaulted = 1,
   }
   ```
2. Add a non-breaking derived interface `IContextualExecutionSessionFactory<TSession> : IExecutionSessionFactory<TSession>`:
   ```csharp
   public interface IContextualExecutionSessionFactory<TSession> : IExecutionSessionFactory<TSession>
       where TSession : class
   {
       TSession CreateSession(SessionLifecycleContext context, CancellationToken cancellationToken);

       void DisposeSession(TSession session, SessionLifecycleContext context);
   }
   ```
   `ExecutionWorker<TSession>` checks `if (_sessionFactory is IContextualExecutionSessionFactory<TSession> contextual)` and passes the stable `WorkerIndex` (`0` for standalone worker, `0..N-1` for pool workers) and monotonically increasing per-worker `SessionGeneration` (`0, 1, 2, ...`), falling back to `IExecutionSessionFactory<TSession>` otherwise.
3. Add worker-indexed factory overloads to `ExecutionWorkerServiceCollectionExtensions` and `ExecutionWorkerHostingExtensions`:
   ```csharp
   public static IServiceCollection AddExecutionWorkerPool<TSession>(
       this IServiceCollection services,
       Func<IServiceProvider, int, IExecutionSessionFactory<TSession>> sessionFactoryResolver,
       Action<ExecutionWorkerPoolOptions>? configure = null)
       where TSession : class;
   ```

#### Acceptance
- When Worker `2` in a 4-worker pool recycles 50 times under `MaxOperationsPerSession = 10`, every `CreateSession` and `DisposeSession` call on Worker `2` receives `WorkerIndex == 2`, `WorkerCount == 4`, and `SessionGeneration == 0..50` on the same dedicated OS thread.
- Existing `IExecutionSessionFactory<TSession>` implementations remain 100% binary- and source-compatible across all 9 TFMs.

### EX-02 (P0): Opt-in eager session creation (`WarmUpSessionsOnStart`)

#### Evidence
- `ExecutionWorker<TSession>.InitializeAsync` starts the worker OS thread and completes readiness before calling `CreateSession`.
- When hosting legacy native/COM DLLs in Kubernetes / Docker (`HEALTHCHECK` polling `/readyz`), two problems occur with purely lazy session creation:
  1. Missing native dependencies, corrupted manifests, or binary-layout mismatches only surface on the first user HTTP request rather than failing startup readiness.
  2. The first burst of concurrent HTTP requests pays a 200–800 ms cold-init penalty (`LoadLibraryEx`, PE patching, catalog/database parsing).

#### Design
1. Add `public bool WarmUpSessionsOnStart { get; set; }` (default `false` for backward compatibility) to `ExecutionWorkerOptions` and `ExecutionWorkerPoolOptions` (propagated from pool options to per-worker options).
2. When `WarmUpSessionsOnStart == true`:
   - `ExecutionWorker<TSession>.InitializeAsync(CancellationToken)` schedules eager session creation on each worker's dedicated thread (after `ApartmentState` configuration!) and awaits completion before `InitializeAsync` completes.
   - Because `ExecutionWorkerPool.InitializeAsync` already runs worker initialization in parallel (`Task.WhenAll`), all `N` workers warm up concurrently in $O(t_{\text{init}})$ wall-clock time while respecting STA thread affinity.
   - Expose `public bool IsSessionInitialized { get; }` on `IExecutionWorker<TSession>` and `public int InitializedWorkerCount { get; }` on `IExecutionWorkerPool<TSession>`.

#### Acceptance
- With `WarmUpSessionsOnStart = true`, `InitializeAsync` creates all `N` sessions on their respective STA/MTA worker threads in parallel; if any worker's `CreateSession` throws, `InitializeAsync` faults immediately with the unwrapped exception and disposes already-started sibling workers cleanly.

### EX-03 (P1): Pooled execution deadline overloads (`TimeSpan timeout`)

#### Evidence
- Every downstream WebApi currently maintains a private `CtsPool` (`TryReset()` pooled `CancellationTokenSource` instances) and `TranslateDeadlineException` helper to distinguish:
  - **Caller cancellation** (`cancellationToken.IsCancellationRequested` -> rethrow `OperationCanceledException` bound to `cancellationToken`), vs
  - **Deadline expiration** (timeout token fired while caller token is not cancelled -> throw `TimeoutException` with configured deadline duration).
- Note: once a work item has started executing native/COM code on the worker thread, synchronous native execution cannot be preempted safely (`Thread.Abort` does not exist and would corrupt process memory); however, queued items waiting in `_channel` **can and should** be skipped immediately when their deadline expires before dequeue!

#### Design
1. Add `public TimeSpan DefaultExecutionTimeout { get; set; } = Timeout.InfiniteTimeSpan;` to `ExecutionWorkerOptions` and `ExecutionWorkerPoolOptions`.
2. Add timeout overloads to `IExecutionWorker<TSession>` and `IExecutionWorkerPool<TSession>`:
   ```csharp
   ValueTask<TResult> ExecuteAsync<TResult>(
       Func<TSession, CancellationToken, TResult> operation,
       TimeSpan timeout,
       CancellationToken cancellationToken = default);
   ```
3. On `net6.0+`, back finite deadlines with an internal lock-free bounded pool of reusable `CancellationTokenSource` instances (`TryReset()` on return when uncancelled) to keep steady-state heap allocations minimal on the hot path.
4. Distinguish queue-time timeout vs in-flight timeout:
   - If the deadline expires **while queued** in `_channel`, skip invoking `operation` on the worker thread, increment `execution.worker.operations` with `outcome="timed_out"`, and complete the caller with `TimeoutException` without stalling the worker!
   - If `operation` throws `OperationCanceledException` after deadline expiry while `cancellationToken.IsCancellationRequested == false`, translate to `TimeoutException`.

#### Acceptance
- Queued items whose `timeout` expires behind a busy worker never invoke `operation`, release pooled `CancellationTokenSource` resources cleanly, and throw `TimeoutException` when `cancellationToken` was not cancelled (or `OperationCanceledException(cancellationToken)` when the caller cancelled).

### EX-04 (P1): Built-in `IHealthCheck` and `ExecutionPoolSnapshot` in `Execution.Hosting`

#### Evidence
- All 30+ ASP.NET Core services write near-identical `/readyz` and `/api/diagnostics` endpoints inspecting `WorkerCount`, `QueueDepth`, `IsAnyFaulted`, and `WorkerFaults`.

#### Design
1. Add `ExecutionPoolSnapshot GetSnapshot()` on `IExecutionWorkerPool<TSession>` returning a single consistent value-type/record snapshot (`WorkerCount`, `InitializedWorkerCount`, `FaultedWorkerCount`, `TotalQueueDepth`, `PerWorkerQueueDepths`, `IsDisposed`).
2. In `AdaskoTheBeAsT.Interop.Execution.Hosting`, add an optional `ExecutionWorkerPoolHealthCheck<TSession>` (`Microsoft.Extensions.Diagnostics.HealthChecks.IHealthCheck` when targeting `net8.0+` or in a lightweight health-checks extension):
   - `Unhealthy` if all workers are faulted, pool is disposed, or startup initialization faulted.
   - `Degraded` if `FaultedWorkerCount > 0` (some workers still healthy) or `TotalQueueDepth` exceeds a configurable warning threshold.
   - `Healthy` otherwise.

#### Acceptance
- Unit tests verify `Healthy`, `Degraded`, and `Unhealthy` transitions and zero-allocation snapshot reads when healthy.

### EX-05 (P2): Optional bounded queue admission (`MaxQueueDepthPerWorker` / `MaxTotalQueueDepth`)

#### Evidence
- `ExecutionWorker<TSession>` currently uses `Channel.CreateUnbounded<WorkItem>`. Under sustained overload against slow native/COM solvers (e.g., 50–300 ms per solve), unbounded queuing increases tail latency without bound instead of allowing ASP.NET Core endpoints to shed load quickly with HTTP `429` / `503`.

#### Design
1. Add `public int? MaxQueueDepth { get; set; }` to `ExecutionWorkerOptions` and `public int? MaxTotalQueueDepth { get; set; }` to `ExecutionWorkerPoolOptions` (`null` default preserves current unbounded behavior).
2. Enforce admission atomically against the existing `_queueDepth` counter before writing to `_channel`, throwing `ExecutionQueueFullException` (carrying `WorkerName`, `CurrentQueueDepth`, and `MaxQueueDepth`) and incrementing `execution.worker.operations` with `outcome="rejected"` when full.

#### Acceptance
- Concurrent stress tests confirm `QueueDepth` never exceeds `MaxQueueDepth` under parallel contention and drains back to `0` cleanly once active work completes.
