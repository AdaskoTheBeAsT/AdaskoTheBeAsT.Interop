## Executive summary

After filtering out everything owned by `Interop.COM`, `Interop.Threading`, `Interop.Unmanaged`, and `EX-01`..`EX-06`, **five concrete execution, DI, and ASP.NET Core gaps** remained across multi-service interop hosts:

1. **String-matched queue-capacity rejections:**
   - `ExecutionWorker<TSession>` rejected excess waiting work when `QueueCapacity > 0` by throwing plain `new InvalidOperationException("The worker admission capacity is exhausted.")`.
   - HTTP endpoints had to match that exact English message literal to return HTTP `503`, and unit tests had to spin up and block a live worker pool just to obtain an instance of that exception.
2. **DI registration bypass (`IExecutionDispatcher<TSession>` & host options):**
   - Domain calculators typically inject `IExecutionDispatcher<TSession>`, yet `AddExecutionWorker<TSession>()` and `AddExecutionWorkerPool<TSession>()` did not forward `IExecutionDispatcher<TSession>` in `IServiceCollection`.
   - Furthermore, real hosts bind strongly typed `IOptions<TSolverConfiguration>` (`WorkerCount`, `QueueCapacity`, `MaxOperationsPerSession`) with `.ValidateOnStart()`, requiring `Action<IServiceProvider, ExecutionWorkerPoolOptions>` to map validated host configuration into `ExecutionWorkerPoolOptions`. Because neither capability existed, hosts hand-rolled `TryAddSingleton` + `AddHostedService` instead of calling `Execution.DependencyInjection` / `Execution.Hosting`.
3. **Boilerplate `*SessionFactory.cs` classes:**
   - Nearly every session factory in downstream interop libraries and benchmark harnesses was a 15–25 line wrapper calling `cancellationToken.ThrowIfCancellationRequested()`, `new TSession(...)`, and `session.Dispose()`.
4. **Duplicated ASP.NET Core Minimal API plumbing & latent fault-serialization bug:**
   - Minimal API hosts duplicated `try / catch` HTTP status mapping (`ArgumentException` -> `400`, aborted `OperationCanceledException` -> `499`, `TimeoutException` / `ObjectDisposedException` / queue saturation -> `503 ProblemDetails`), `/healthz` + `/readyz` wiring, and `GET /api/diagnostics => TypedResults.Ok(pool.GetSnapshot())` with `[JsonSerializable(typeof(ExecutionWorkerPoolSnapshot))]`.
   - **Latent production bug in raw snapshot JSON serialization:** `ExecutionWorkerSnapshot.Fault` is typed as `System.Exception?`. While healthy (`Fault == null`), source-generated `System.Text.Json` succeeds; once a worker actually faults (`Fault != null`), serializing `ExecutionWorkerPoolSnapshot` directly throws `NotSupportedException` on `Exception.TargetSite` (`MethodBase`) and risks disclosing internal stack traces over HTTP.
5. **Missing dedicated-thread `MaxStackSize` & worker-thread-affine lifecycle hooks (`OnWorkerThreadStart` / `CreateWorkerThreadScope`):**
   - 32-bit Compaq Visual Fortran, Borland Delphi, PowerBASIC, and VB6 engines running on `ExecutionWorkerPool<TSession>` inside constrained `win-x86` 2–4 GiB virtual address spaces benefit from explicit `new Thread(RunWorkerLoop, maxStackSize)` sizing to prevent both native stack overflow and excessive default stack reservation across multi-worker hosts.
   - `BeforeThreadStart` runs on the **calling** thread before `Thread.Start()`, whereas thread-affine one-time worker setup and teardown (such as STA `"OleMainThreadWndClass"` pre-warming or worker-lifetime `StaApartmentScope` / `ComAutomationLocaleScope` / `NativeExecutionScope` / shared `IComActivationScope` leases across session recyclings) needs callbacks that create and dispose thread-affine `IDisposable` scopes **on the dedicated worker thread itself** before the first `CreateSession` and after the final `DisposeSession`.

## Detailed technical plan

### EX-07 (P0): Typed `ExecutionAdmissionRejectedException` preserving `InvalidOperationException` compatibility

#### Evidence
- `ExecutionWorker.cs` rejected saturated bounded-queue submissions with plain `InvalidOperationException`:
  ```csharp
  workItem.TrySetException(new InvalidOperationException("The worker admission capacity is exhausted."));
  ```
- Downstream HTTP endpoints were forced to match the exact message string:
  ```csharp
  catch (Exception exception) when (exception is TimeoutException or ObjectDisposedException
                                    || exception is InvalidOperationException
                                    {
                                        Message: "The worker admission capacity is exhausted.",
                                    })
  ```
- Downstream endpoint unit tests had to spin up a real `ExecutionWorkerPool<object>` with `ManualResetEventSlim` just to capture a genuine rejection exception instance.

#### Design
1. Add `ExecutionAdmissionRejectedException` in `AdaskoTheBeAsT.Interop.Execution` deriving from `InvalidOperationException`:
   ```csharp
   public sealed class ExecutionAdmissionRejectedException : InvalidOperationException
   {
       public const string DefaultMessage = "The worker admission capacity is exhausted.";

       public ExecutionAdmissionRejectedException();
       public ExecutionAdmissionRejectedException(string message);
       public ExecutionAdmissionRejectedException(string message, Exception innerException);
       public ExecutionAdmissionRejectedException(string? workerName, int queueCapacity, string? message = null);

       public string? WorkerName { get; }
       public int QueueCapacity { get; }
   }
   ```
   *(On `.NET Framework` targets where `[Serializable]` serialization constructors apply, follow existing exception conventions in the repo.)*
2. Update `ExecutionWorker<TSession>.Submit` (`QueueCapacity > 0` rejection path) to pass `new ExecutionAdmissionRejectedException(_options.Name, capacity)` to `workItem.TrySetException(...)`.
3. Keep `ExecutionWorkerOptions.QueueCapacity`, `ExecutionWorkerPoolOptions.QueueCapacity`, `DefaultMessage`, and the `InvalidOperationException` base type unchanged so every existing `catch (InvalidOperationException)` and message assertion continues to pass without modification (`EX-05` regression gate preserved).

#### Acceptance
- Existing `EX-05` `InvalidOperationException` capacity tests continue to pass unchanged across all 5 TFMs (`net11.0`, `net10.0`, `net481`, `net48`, `net472`).
- New unit tests verify catching `ExecutionAdmissionRejectedException` directly on both `ExecuteAsync` and `ExecuteValueAsync` (worker and pool), inspecting `WorkerName` and `QueueCapacity`, and constructing instances directly in unit tests without spinning up a live worker.

### EX-08 (P0): `IExecutionDispatcher<TSession>` DI forwarding, `IServiceProvider`-aware options configuration, and `ValidateOnStart`

#### Evidence
- `ExecutionWorkerServiceCollectionExtensions` registered only `IExecutionWorker<TSession>` or `IExecutionWorkerPool<TSession>`, never `IExecutionDispatcher<TSession>`.
- Downstream DI extensions therefore had to bypass `AddExecutionWorkerPool<TSession>()` and register everything manually:
  ```csharp
  services.TryAddSingleton<IExecutionWorkerPool<NativeSolverSession>>(sp =>
  {
      var configuration = sp.GetRequiredService<IOptions<NativeSolverConfiguration>>().Value;
      return new ExecutionWorkerPool<NativeSolverSession>(...);
  });
  services.TryAddSingleton<IExecutionDispatcher<NativeSolverSession>>(sp =>
      sp.GetRequiredService<IExecutionWorkerPool<NativeSolverSession>>());
  services.AddHostedService<ExecutionWorkerPoolHostedService<NativeSolverSession>>();
  ```

#### Design
1. **Forward `IExecutionDispatcher<TSession>` automatically:**
   - `AddExecutionWorker<TSession>` registers `services.TryAddSingleton<IExecutionDispatcher<TSession>>(static sp => sp.GetRequiredService<IExecutionWorker<TSession>>());`.
   - `AddExecutionWorkerPool<TSession>` registers `services.TryAddSingleton<IExecutionDispatcher<TSession>>(static sp => sp.GetRequiredService<IExecutionWorkerPool<TSession>>());`.
   - Because `TryAddSingleton` is used, if an application explicitly registers a custom `IExecutionDispatcher<TSession>` decorator first, the first registration wins predictably.
2. **Add `IServiceProvider`-aware options configuration overloads:**
   - In `ExecutionWorkerServiceCollectionExtensions`:
     ```csharp
     public static IServiceCollection AddExecutionWorker<TSession>(
         this IServiceCollection services,
         Action<IServiceProvider, ExecutionWorkerOptions> configure)
         where TSession : class;

     public static IServiceCollection AddExecutionWorkerPool<TSession>(
         this IServiceCollection services,
         Action<IServiceProvider, ExecutionWorkerPoolOptions> configure)
         where TSession : class;

     public static IServiceCollection AddExecutionWorkerPool<TSession>(
         this IServiceCollection services,
         Func<IServiceProvider, int, IExecutionSessionFactory<TSession>> sessionFactoryResolver,
         Action<IServiceProvider, ExecutionWorkerPoolOptions> configure)
         where TSession : class;
     ```
   - Mirror the same `Action<IServiceProvider, ...>` overloads on `AddExecutionWorkerHostedService<TSession>` and `AddExecutionWorkerPoolHostedService<TSession>` in `ExecutionWorkerHostingExtensions`.
   - Wire named options via `services.AddOptions<TOptions>(optionsName).Configure<IServiceProvider>((options, sp) => configure(sp, options))` and register an `IValidateOptions<ExecutionWorkerOptions>` / `IValidateOptions<ExecutionWorkerPoolOptions>` validator invoking `options.Validate()` with `.ValidateOnStart()` so invalid `WorkerCount`, `QueueCapacity`, `MaxOperationsPerSession`, `DisposeTimeout`, or `MaxStackSize` fail fast during `IHost.StartAsync` even before the first resolution.

#### Acceptance
- Resolving `IExecutionDispatcher<TSession>` from a container configured via `AddExecutionWorker<TSession>()` or `AddExecutionWorkerPool<TSession>()` returns the exact same singleton instance as `IExecutionWorker<TSession>` / `IExecutionWorkerPool<TSession>`.
- Host startup fails fast with `OptionsValidationException` when `Action<IServiceProvider, ExecutionWorkerPoolOptions>` sets an out-of-range `WorkerCount <= 0`, negative `QueueCapacity`, or invalid `DisposeTimeout`.
- Calling `AddExecutionWorkerPoolHostedService<TSession>` twice is idempotent (creates one pool and one `IHostedService`).

### EX-09 (P1): `DelegateExecutionSessionFactory<TSession>` and delegate-based DI/Hosting registration

#### Evidence
- Downstream `*SessionFactory.cs` classes and benchmark harnesses repeatedly implemented `IExecutionSessionFactory<TSession>` solely to invoke a constructor delegate and dispose `IDisposable` sessions (having to suppress `IDISP007` in each file).

#### Design
1. Add `DelegateExecutionSessionFactory<TSession> : ContextualExecutionSessionFactory<TSession>` in `AdaskoTheBeAsT.Interop.Execution`:
   ```csharp
   public sealed class DelegateExecutionSessionFactory<TSession>
       : ContextualExecutionSessionFactory<TSession>
       where TSession : class
   {
       public DelegateExecutionSessionFactory(
           Func<CancellationToken, TSession> createSession,
           Action<TSession>? disposeSession = null);

       public DelegateExecutionSessionFactory(
           Func<SessionLifecycleContext, CancellationToken, TSession> createSession,
           Action<TSession, SessionLifecycleContext>? disposeSession = null);

       public override TSession CreateSession(
           SessionLifecycleContext context,
           CancellationToken cancellationToken);

       public override void DisposeSession(
           TSession session,
           SessionLifecycleContext context);
   }
   ```
   - Checks `cancellationToken.ThrowIfCancellationRequested()` before invoking `createSession`.
   - When `disposeSession` is `null`, defaults to `(session as IDisposable)?.Dispose()`.
2. Add concise factory-delegate overloads to `ExecutionWorkerServiceCollectionExtensions` and `ExecutionWorkerHostingExtensions`:
   ```csharp
   public static IServiceCollection AddExecutionWorker<TSession>(
       this IServiceCollection services,
       Func<IServiceProvider, SessionLifecycleContext, CancellationToken, TSession> createSession,
       Action<IServiceProvider, ExecutionWorkerOptions>? configure = null,
       Action<TSession, SessionLifecycleContext>? disposeSession = null)
       where TSession : class;

   public static IServiceCollection AddExecutionWorkerPool<TSession>(
       this IServiceCollection services,
       Func<IServiceProvider, SessionLifecycleContext, CancellationToken, TSession> createSession,
       Action<IServiceProvider, ExecutionWorkerPoolOptions>? configure = null,
       Action<TSession, SessionLifecycleContext>? disposeSession = null)
       where TSession : class;
   ```
   *(Plus matching `AddExecutionWorkerHostedService<TSession>` and `AddExecutionWorkerPoolHostedService<TSession>` overloads.)*

#### Acceptance
- Standalone workers, pools, and hosted services can register and recycle `IDisposable` sessions using a single lambda without defining a custom `IExecutionSessionFactory<TSession>` class.
- Default disposal invokes `IDisposable.Dispose()` when `TSession` implements `IDisposable`, is a safe no-op for non-disposable `TSession`, and invokes custom `disposeSession` when supplied.

### EX-10 (P1): Companion package `AdaskoTheBeAsT.Interop.Execution.AspNetCore` (`net11.0;net10.0`)

#### Evidence
- Downstream ASP.NET Core Minimal API projects duplicated:
  1. Endpoint `try / catch` blocks mapping `ArgumentException` -> `400`, caller `OperationCanceledException` -> `499`, and `TimeoutException` / `ObjectDisposedException` / `ExecutionAdmissionRejectedException` -> `503` `ProblemDetails`.
  2. `GET /api/diagnostics` returning `pool.GetSnapshot()` paired with `[JsonSerializable(typeof(ExecutionWorkerPoolSnapshot))]`, which fails at runtime with `NotSupportedException` (`System.Reflection.MethodBase` on `Exception.TargetSite`) whenever a worker faults (`Fault != null`).
  3. `/healthz` (liveness, `Predicate = static _ => false`) + `/readyz` (readiness, `tags.Contains("ready")`) endpoint wiring.

#### Design
1. Create `src/AdaskoTheBeAsT.Interop.Execution.AspNetCore/AdaskoTheBeAsT.Interop.Execution.AspNetCore.csproj` (and matching `test/unit/AdaskoTheBeAsT.Interop.Execution.AspNetCore.Test`):
   - `<TargetFrameworks>net11.0;net10.0</TargetFrameworks>` (modern ASP.NET Core TFMs only; `.NET Framework` is intentionally excluded because `Microsoft.AspNetCore.App` is modern-.NET-only).
   - `<FrameworkReference Include="Microsoft.AspNetCore.App" />` + project references to `Execution`, `Execution.DependencyInjection`, and `Execution.Hosting` (zero third-party NuGet dependencies).
2. **Execution endpoint filter & `IExceptionHandler`:**
   - `ExecutionEndpointFilter` (`IEndpointFilter`) + `RouteHandlerBuilder.WithExecutionExceptionHandling(string? unavailableTitle = null)` / `RouteGroupBuilder.WithExecutionExceptionHandling(...)` (and optional global `ExecutionExceptionHandler : IExceptionHandler` registered via `AddExecutionExceptionHandler()`):
     - `ArgumentException` -> `400 Bad Request` `ProblemDetails` (generic safe title, never echoing raw native paths or stack traces).
     - `OperationCanceledException` when `httpContext.RequestAborted.IsCancellationRequested` -> `499 Client Closed Request` (`StatusCodes.Status499ClientClosedRequest`).
     - `TimeoutException`, `ObjectDisposedException`, or `ExecutionAdmissionRejectedException` -> `503 Service Unavailable` `ProblemDetails` (optional `Retry-After` header via `ExecutionAspNetCoreOptions`).
3. **AOT-safe, leak-free diagnostics DTOs & endpoint helpers:**
   - Define immutable, reflection-free DTOs (`ExecutionWorkerDiagnosticsDto` and `ExecutionWorkerPoolDiagnosticsDto`) backed by `public partial class ExecutionAspNetCoreJsonSerializerContext : JsonSerializerContext` (`JsonKnownNamingPolicy.CamelCase`):
     - Carries `Name`, `QueueDepth`, `IsInitialized`, `IsDisposed`, `IsFaulted`, and `FaultType` (`fault?.GetType().Name` — **never** raw `System.Exception`, `TargetSite`, or `StackTrace`).
     - Pool DTO carries `Name`, `WorkerCount`, `QueueDepth`, `InitializedWorkerCount`, `FaultedWorkerCount`, `IsAnyFaulted`, `IsInitialized`, `IsDisposed`, and `IReadOnlyList<ExecutionWorkerDiagnosticsDto> Workers` using camelCase JSON property names (`workerCount`, `queueDepth`, `isAnyFaulted`, etc.).
   - Add `IEndpointRouteBuilder.MapExecutionWorkerDiagnostics<TSession>(string pattern = "/api/diagnostics")` and `MapExecutionWorkerPoolDiagnostics<TSession>(string pattern = "/api/diagnostics")`.
   - Add `IServiceCollection.AddExecutionAspNetCoreJson()` (inserting `ExecutionAspNetCoreJsonSerializerContext.Default` into `HttpJsonOptions.SerializerOptions.TypeInfoResolverChain`) and optional `IEndpointRouteBuilder.MapExecutionHealthProbes(string livenessPattern = "/healthz", string readinessPattern = "/readyz", string readyTag = "ready")`.

#### Acceptance
- Minimal API test host (`TestServer`) on both `net11.0` and `net10.0` verifies:
  - `200 OK` normal calculation pass-through,
  - `400 Bad Request` on `ArgumentException`,
  - `499` when `RequestAborted` cancels,
  - `503 Service Unavailable` `ProblemDetails` on `TimeoutException`, `ExecutionAdmissionRejectedException`, and `ObjectDisposedException`,
  - `GET /api/diagnostics` succeeds with source-generated JSON **both when healthy and when one or all workers are faulted** (`Fault != null`), emitting `faultType` without throwing `NotSupportedException` or leaking stack traces,
  - `/healthz` and `/readyz` reflect startup, partial worker fault (`Degraded`), and total fault/disposal (`Unhealthy`).

### EX-11 (P2): Configurable `MaxStackSize`, worker-thread-affine `OnWorkerThreadStart`, and worker-thread-disposed `CreateWorkerThreadScope`

#### Evidence
- Stateful 32-bit Compaq Visual Fortran, Borland Delphi, PowerBASIC, and VB6 engines running on `ExecutionWorkerPool<TSession>` inside `win-x86` 2–4 GiB virtual address spaces need explicit stack sizing on dedicated worker threads.
- `ExecutionWorkerOptions.BeforeThreadStart` runs synchronously on the **caller** thread before `Thread.Start()`, whereas thread-affine worker setup (such as CoreCLR STA `"OleMainThreadWndClass"` pre-warming, initial `CultureInfo` / Win32 `LCID` configuration, or thread error-mode configuration) must run once on the dedicated worker `Thread` itself before the first `CreateSession` and remain active across session recyclings.
- Furthermore, thread-affine scopes from sibling libraries (`StaApartment.EnterScope()`, `ComAutomationLocaleScope.Enter()`, `NativeExecutionGuard.EnterScope()`, or a worker-lifetime `Executor.Activate(...)` shared across session recyclings) return an `IDisposable` whose `Dispose()` **must execute on that exact dedicated worker thread** during worker shutdown after the final `DisposeSession()`.

#### Design
1. Add `public int MaxStackSize { get; set; }` (`0` default = runtime/PE default stack size) to both `ExecutionWorkerOptions` and `ExecutionWorkerPoolOptions`:
   - `Validate()` throws `ArgumentOutOfRangeException(nameof(MaxStackSize))` when `MaxStackSize < 0`.
   - `ExecutionWorker<TSession>` constructs the dedicated worker thread via `MaxStackSize > 0 ? new Thread(RunWorkerLoop, MaxStackSize) : new Thread(RunWorkerLoop)`, and `ExecutionWorkerPool<TSession>` propagates `MaxStackSize` to each child worker's `ExecutionWorkerOptions`.
2. Add worker-thread-affine startup and scope lifecycle hooks:
   - `public Action? OnWorkerThreadStart { get; set; }` and `public Func<IDisposable?>? CreateWorkerThreadScope { get; set; }` on `ExecutionWorkerOptions`.
   - `public Action<int>? OnWorkerThreadStart { get; set; }` and `public Func<int, IDisposable?>? CreateWorkerThreadScope { get; set; }` on `ExecutionWorkerPoolOptions` (receiving `workerIndex` `0..WorkerCount - 1`, mapped to `() => poolCallback(workerIndex)` on each child worker, and copied in `Snapshot()`).
   - Lifecycle order on the dedicated worker thread inside `ExecutionWorker.Process`:
     1. `OnWorkerThreadStart?.Invoke()` runs **once** at the top of `Process` (where `Environment.CurrentManagedThreadId` is the dedicated worker thread and `ApartmentState.STA` is already active when `UseStaThread = true`).
     2. `workerThreadScope = CreateWorkerThreadScope?.Invoke()` runs **once** immediately after `OnWorkerThreadStart` and **before** `EnsureSessionCreated(...)`, remaining alive across `MaxOperationsPerSession` and fault-triggered session recyclings.
     3. In `Process.finally`, **after** `DisposeSession()` completes, `workerThreadScope?.Dispose()` runs **once** on the exact same dedicated worker thread before `_workerExitCompletionSource` signals completion.
   - If `OnWorkerThreadStart`, `CreateWorkerThreadScope`, or `workerThreadScope.Dispose()` throws, any already-created scope is still cleaned up and the worker transitions cleanly into its faulted state (`ExecutionWorkerSnapshot.Fault` populated, `InitializeAsync` / pending work faulted) rather than crashing the process with an unhandled thread exception.

#### Acceptance
- Unit tests across all 5 TFMs (`net11.0`, `net10.0`, `net481`, `net48`, `net472`) verify negative `MaxStackSize` rejection, positive `MaxStackSize` propagation to `ExecutionWorker` and `ExecutionWorkerPool`, `OnWorkerThreadStart` and `CreateWorkerThreadScope` executing strictly once on the dedicated worker thread (preserving `ManagedThreadId` and `ApartmentState.STA`, surviving `MaxOperationsPerSession` recycles, and disposing `workerThreadScope` on the same `ManagedThreadId` strictly after `DisposeSession`), and deterministic worker fault handling when startup or scope disposal throws.
